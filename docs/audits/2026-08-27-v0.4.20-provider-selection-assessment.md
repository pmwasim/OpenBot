# OpenBot v0.4.20 provider-selection assessment

Date: 2026-08-27  
Implementation commit: `66162a5e62a72a23043b15ab31f0a81f952cc57a`

## Outcome

OpenBot v0.4.20 turns the compatible provider adapter into a usable, generic opt-in path. It discovers models from `/v1/models` and sends structured agent requests to `/v1/chat/completions`. Operators can choose the provider and model per task from the dashboard or CLI, and the selected provider is retained in task metadata and model audit events.

The local model remains the default. Local-only mode refuses external providers, while remote use requires explicit `OPENBOT_LOCAL_ONLY=0` and `OPENBOT_REMOTE_BASE_URL`; an API key is optional and is sent only as an authorization header when configured. This release does not claim support for a named commercial provider or a complete credential-management UI.

## Product assessment

This closes the provider-choice gap without adding a dependency or making remote access part of the default installation. The dashboard and CLI now expose the same explicit provider/model decision, and the server remains the source of truth for provider availability and model selection. A free local installation remains complete enough to run without an account, hosted service, GPU, or mandatory spend.

The compatible endpoint is intentionally narrow: model listing and structured chat are supported, while provider-specific OAuth, usage accounting, streaming parity, and richer credential management remain future work. Remote provider cost, availability, and data handling remain operator-controlled concerns.

## Security and privacy assessment

Remote requests use a bounded timeout and propagate task cancellation. The configured API key is not included in provider descriptions, task payloads, model context, or audit output; endpoint userinfo is stripped from public descriptions. The provider selector is rendered through DOM text nodes, and arbitrary provider/model values are validated by the server before agent execution. Existing approval, policy, workspace, authentication, audit, and local-only controls remain in the execution path.

## Remaining gaps

Provider settings and secret storage UX, OAuth-capable adapters, usage accounting, provider streaming parity, desktop automation, connectors, signed extensions, collaboration, multi-user authentication, remote workers, and full-duplex clients remain future work. These are intentionally not represented as completed by v0.4.20.
