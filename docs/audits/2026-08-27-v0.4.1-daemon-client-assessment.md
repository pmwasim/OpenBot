# OpenBot v0.4.1 daemon client assessment

Date: 2026-08-27  
Scope: shared-daemon CLI chat parity  
Audited implementation commit: 20e9d0806947beb46dfc6e4cd4fb7ac48c6d7411

## Product result

OpenBot's CLI can now route a chat through the running local daemon with `node cli/openbot.mjs chat --daemon`. The daemon owns the task, agent controller, approvals, audit events, routines, and dashboard-visible state. The CLI can use the default local daemon URL or an explicitly configured endpoint; a configured bearer token is attached for an explicitly protected LAN deployment. The existing direct local controller path remains available for administration and compatibility.

This moves OpenBot closer to the reference agent concept of multiple clients working against durable role- and task-specific state, while keeping execution on the operator's machine and preserving the approval boundary. It does not claim shared live streaming or hosted execution yet.

## Evidence

- The release harness passed 85/85 checks, including daemon-routed CLI chat and confirmation that the task is persisted by the server.
- The client accepts structured JSON responses, converts daemon/network failures into bounded CLI errors, and attaches `OPENBOT_AUTH_TOKEN` only when configured.
- The daemon path supports general chat and named-bot chat routes, preserving the server's existing workspace, skill, model, approval, and recovery checks.
- No runtime dependency, hosted service, account, telemetry, or paid integration was added.

## Older-laptop assessment

The client uses the stock Node.js `fetch` API and one bounded request per chat call. It does not add a second model process or require Docker. Detached daemon mode keeps the local scheduler and task store available after the terminal closes while the host remains powered. Natural-language work still depends on a compatible local model runtime.

## Security boundary

The daemon remains loopback-only by default. The optional daemon URL is an explicit operator setting, and non-loopback server access still requires the configured bearer token. Client responses are parsed as JSON and non-success responses become CLI errors; model text still reaches workers only through the daemon's strict agent contract and policy engine. No client flag bypasses workspace containment, approvals, or audit recording.

## Remaining gaps

- The shared client uses request/response chat rather than a live event stream; concurrent UI updates and CLI event streaming remain future work.
- CLI administration still operates directly on the configured local store, and there is no general remote client for every command.
- No OS-installed user service, automatic restart policy, notifications, desktop automation, connectors, multi-user identity, or remote workers are included.
