# OpenBot v0.4.35 task-queue assessment

Release: v0.4.35  
Assessment date: 2026-08-27  
Scope: bounded daemon admission and old-laptop resource behavior.

## Product outcome

OpenBot now admits asynchronous daemon tasks through a small FIFO queue. The selected resource profile controls active capacity and waiting depth: legacy uses one active task and four waiting slots, while standard uses two active tasks and eight waiting slots. Queue state is returned to clients as `started` or `queued`, and a full waiting queue is rejected with HTTP 429.

## Safety and reliability assessment

- Queue admission is in-process and bounded; it does not create unbounded memory pressure.
- Duplicate task submissions are rejected while a task is active or queued.
- Routine execution uses the same queue as asynchronous daemon tasks.
- Existing task identity, workspace, provider, approval, cancellation, and audit paths remain authoritative when queued work starts.
- Queue capacity is capped even when environment overrides are supplied.
- No dependency, account, background service, remote worker, or mandatory spend is introduced.

## Old-laptop assessment

The legacy profile serializes model work and limits waiting backlog. Standard mode permits limited parallelism for stronger hardware. Queueing does not alter agent turn, action, context, shell, browser, connector, or model time limits; it only prevents excessive simultaneous work.

## Verification evidence

- Red phase: the release harness failed because `lib/task-queue.mjs` did not exist.
- Green phase: queue serialization, FIFO completion, duplicate/backlog bounds, resource-profile defaults, public settings, API wiring, and existing full release coverage pass after implementation.

## Known limits

The queue is process-local and is not a distributed scheduler. Restarting the daemon loses in-memory waiting submissions; durable tasks remain in the store and can be started again. Queueing is not a sandbox and cannot make a large model fast on every laptop.
