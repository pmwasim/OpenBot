# OpenBot v0.4.0 daemon lifecycle assessment

Date: 2026-08-27  
Scope: portable local daemon operation on older laptops  
Release commit: to be recorded after final verification

## Product result

OpenBot now has a usable local background mode in addition to its foreground server. An operator can start the daemon with `node cli/openbot.mjs start --detach`, inspect it with `status`, and stop it with `stop`. A second start reuses the existing daemon instead of creating a duplicate process. The daemon process record and runtime log stay in the configured data directory, so the workflow remains local and does not require a hosted account, paid service, container, or additional runtime package.

This addresses an important part of the reference agent concept: a named local bot can continue bounded scheduled or interactive work after the operator closes the terminal. The boundary is explicit: work continues only while the host is running and available. Sleep, shutdown, crashes, and model-runtime unavailability still require local recovery or resume; OpenBot does not claim cloud execution.

## Evidence

- The release harness passed 83/83 checks, including detached start, status, duplicate-start protection, clean stop, and stopped-state reporting.
- The daemon uses a 0600 process record, removes stale records, refuses a live duplicate record, and releases its record on signal shutdown.
- `status` reports daemon reachability and local model health separately, so a running daemon with no model is distinguishable from a stopped daemon.
- Existing agent, approval, task recovery, memory, skills, bots, routines, workspace, symlink, browser, shell, audit-redaction, LAN-authentication, and public-surface checks remain in the same harness.
- No runtime dependency, hosted service, account, telemetry, or paid integration was added.

## Older-laptop assessment

The lifecycle implementation uses the stock Node.js process and filesystem APIs, one detached child process, one lightweight health request during startup/status, and the existing in-process scheduler. It does not require Docker in the `legacy` resource profile. Natural-language work still depends on an installed compatible local model runtime and may be too slow or unavailable on some hardware; core administration and allowlisted diagnostics remain usable without one.

## Security boundary

The daemon remains loopback-only by default. Existing non-loopback authentication, request bounds, workspace containment, approval binding, output limits, and audit redaction are unchanged. The PID record is not an authorization mechanism; it is only local process coordination. The daemon must not be exposed directly to the public internet.

## Remaining gaps

- CLI chat and administration still open the local store directly rather than being a complete remote client of the daemon; shared multi-client streaming remains future work.
- No OS-installed user service, automatic restart policy, notifications, or power-management integration is included.
- Provider credentials, richer adapters, connectors, desktop automation, multi-user identity, and remote workers remain incomplete.
- A local model runtime is still required for natural-language reasoning.
