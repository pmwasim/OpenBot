# OpenBot v0.4.17 CLI task follow assessment

Date: 2026-08-27
Implementation commit: `de08eecd0060aeca404263b03f129a7c6255e630`
Scope: lightweight CLI submission, daemon execution, incremental task-event following, and compatibility behavior.

## Outcome

The CLI now supports `run --daemon --follow`. It creates a durable task through the shared local daemon, starts it through the existing asynchronous task boundary, follows bounded event history using the existing offset API, and returns the final persisted task plus events in JSON mode. Human-readable mode reports event milestones on stderr and the final result on stdout.

The existing `run` command remains create-only unless `--follow` is explicitly selected. The direct local path, task controls, approval gates, workspace validation, cancellation, model limits, and audit history remain unchanged.

## Evidence

- `npm run check`: 103/103 passed.
- `node --check cli/openbot.mjs` and `node --check lib/client.mjs`: passed.

- End-to-end coverage proves daemon task creation, `202` asynchronous start, incremental event follow, completed status, final persisted result, and non-empty event history.

- No runtime package or hosted service was added; the feature uses stock Node.js and the existing local daemon API.

## Product assessment

This closes a concrete P0 client gap: a terminal operator can now submit and monitor a real durable bot task without keeping a synchronous request open or using the dashboard. It also gives scripts a bounded JSON result containing the task identity and event trail.

The follow loop stops at completed, failed, cancelled, paused, or waiting-for-approval states. Approval and task control remain separate explicit commands, so following does not auto-approve consequential work.

## Older-laptop and security assessment

The feature is suitable for the legacy CPU-only profile. It adds no model process, worker, container, native shell, or dependency; it makes one bounded daemon request per event poll and inherits the existing local model, turn/action, request, and output limits.

The client sends only the task id, event offset, and already validated task-start payload. Server-side task, workspace, bot, skill, policy, approval, loopback, optional bearer-authentication, and redaction controls remain authoritative. The final exact tree requires the independent security scan recorded for this release.

## Remaining gaps

Full-duplex streaming, native desktop packaging, push notifications, multi-user identity, connectors, signed extensions, and remote workers remain future work. OpenBot remains local-first and zero-cost by default; optional external services are not required for this capability.
