# OpenBot v0.4.34 failed-task retry assessment

Release: v0.4.34  
Assessment date: 2026-08-27  
Scope: bounded recovery for terminally failed tasks.

## Product outcome

OpenBot now provides a practical recovery path when local model or worker work fails. Operators can retry a failed task from the dashboard, `POST /api/tasks/:id/retry`, or `openbot retry <task-id>`. The same task identity and workspace are retained, while the retry is recorded as a durable event.

## Safety assessment

- Only `failed` tasks are retryable.
- Retry attempts are capped at three per task and the count is persisted in the task projection.
- The old `result` and `error` fields are cleared before the retry begins, preventing stale terminal output from being presented as current work.
- A retry does not reuse a consumed approval. Consequential actions return to the normal fresh approval gate.
- API, CLI, and dashboard are thin clients; store transitions remain authoritative.
- No new dependency, account, background service, remote worker, or mandatory spend is introduced.

## Old-laptop assessment

Retry uses the existing bounded agent limits and provider configuration. It does not increase turns, actions, context size, or model requirements. This makes transient local failures recoverable without weakening the resource profile.

## Verification evidence

- `npm run check` — PASS, 147/147 release checks.
- Coverage includes cross-client retry wiring, failed-only transition, durable retry events, stale-outcome clearing, three-attempt cap, existing approval behavior, task identity, workspace binding, cancellation, recovery, redaction, and public-surface checks.

## Known limits

Retry is not rollback: effects completed before a failure remain completed. It is also not automatic infinite retry; operators must explicitly request each bounded attempt. Failed task retention, richer retry policy, and full audit replay remain separate roadmap work.

## Release gate

Release is eligible after the standard repository security scan reports complete coverage and zero reportable findings on the final commit, followed by terminal verification of the pushed commit, tag, release state, and clean worktree.
